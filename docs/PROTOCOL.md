# 实况智能体 · 统一事件协议 v1

> 这份文档和 `protocol/events.mjs` 是**同一份契约**的两种形态：
> 代码里是可以跑的校验，这里是给人看的规格。
> 两者不一致时以代码为准 —— 但那就是 bug，请改其中一个。

---

## 0. 一句话

**任何智能体，只要能把"工具调用开始/结束"打成一行行 JSON，就能接上实况智能体。**

协议只有 3 个事件类型、6 个字段。没有嵌套、没有版本协商、没有必需的工具注册表。
复杂度全在被故意砍掉的那部分 —— 因为每多一个必填字段，就多一个"接不进来"的理由。

---

## 1. 事件类型

| kind | 含义 | 画面上的效果 |
|---|---|---|
| `tool` | 工具调用**开始** | 一只敌人出场 |
| `tool_end` | 工具调用**结束** | 这只敌人被击杀（`ok:false` 则记为失败） |
| `turn_end` | 本轮结束 | 清场 |

只有这三个，因为消费方 `director.mjs` 的 `handle()` 只实现了这三个。
**协议不发明消费方没实现的类型** —— 那只会造出一堆"文档里有、画面上没有"的事件。

未知 `kind` **不会崩、不会被丢弃、不会被猜成某个已知类型**，
只会被计入 `unknown` 计数并在 doctor 里报出来。详见 §5。

---

## 2. 字段表

| 字段 | 类型 | `tool` | `tool_end` | `turn_end` | 语义 |
|---|---|---|---|---|---|
| `kind` | string | **必填** | **必填** | **必填** | 事件类型，见 §1 |
| `tool` | string | **必填** | 可选 | — | 工具名（**原始名**，不做映射）。空串非法 |
| `id` | string\|number | 强烈建议 | 强烈建议 | — | 调用标识。**配对主键**，见 §4 |
| `ts` | number | **必填** | **必填** | **必填** | 事件时刻（毫秒） |
| `realMs` | number | 可选 | 可选 | — | 这次调用的真实耗时（毫秒），不能为负 |
| `ok` | boolean | 可选 | **必填** | 可选 | 成功与否。`false` = 失败 |

### 每个字段为什么是这个约束

- **`tool` 在 `tool_end` 上不是必填** —— 真实数据里 `tool_result` 常常只有
  `tool_use_id` 没有工具名（Claude Code 就是这样）。而 `director` 在**有 id 时
  按 callId 精确匹配，根本不读 `ev.tool`**。强行要求会逼适配器去猜一个名字填上，
  那正是本项目最不能接受的事。缺了只给一条 warn。

- **`ts` 三个 kind 都必填** —— 拿不到时间的事件无法放到时间轴上。
  与其补一个假时刻，不如明确拒收（见 §5"不伪造"）。

- **`ok` 在 `tool` 上可选、且带 `ok` 有特殊含义** —— 带 `ok` 的 `tool` 表示
  "这是一条**已完成**的一次性事件"，`director` 会生成后立刻结算。
  这是给"一次性给结果"的数据源留的口子。

- **`id` 是建议而非必填** —— 没有 id 时 `director` 会退回"同工具 FIFO"配对。
  能用，但同名工具的多次调用就无法区分了。所以缺 id 会给 warn，
  并且在配对报告里**单独统计**，不混进"按 id 配对"假装精确。

### 扩展字段

协议之外的字段**原样透传、不校验、不丢弃**。
接入方可以带 `sessionId`、`cost`、`vendor` 之类，只要不和上面 6 个重名。

## 3. 三个完整示例

### 3.1 最小可用的两条（一次调用）

```json
{"kind":"tool","tool":"read_file","id":"call_00_kL2Mw1","ts":0}
{"kind":"tool_end","tool":"read_file","id":"call_00_kL2Mw1","ok":true,"ts":799,"realMs":799}
```

`ts` 用的是**播放时间轴**上的毫秒（`build-events.mjs` 折叠过空白间隔）。
实时源可以直接用墙钟，只要同一数据源内是同一把尺子。

### 3.2 失败 + 耗时

```json
{"kind":"tool","tool":"pwsh","id":"call_01","ts":1000}
{"kind":"tool_end","tool":"pwsh","id":"call_01","ok":false,"ts":1383,"realMs":383}
```

`ok:false` 在画面上是暗红的 `FAIL` 飘字，比击杀更弱 —— 失败不该有成就感。

### 3.3 一次性事件 + 收尾

```json
{"kind":"tool","tool":"agent_run","id":"sub-1","ok":true,"ts":2000,"realMs":42000}
{"kind":"turn_end","ok":true,"ts":2450}
```

第一条同时是"开始"和"结果"（带了 `ok`），`agent_run` 是 BOSS。
`turn_end` 清场。

## 4. `id` 配对规则（回归红线）

> **历史事故**：292 次工具调用曾被统计成 **283** 次。
> 原因不是数据处理错，而是**配对口径**写错了 —— 按**工具名**配对。
> 真实数据里 `read` 被调用 87 次、`pwsh` 106 次，每次都是独立 callId；
> 按工具名算，同名调用全被当成"重复上报"丢掉，于是 292 缩成 283。

规则（`PAIRING_RULES`，与代码同一份）：

1. **配对键 = `String(ev.id)`**。不是工具名，不是 `kind+id`。
2. 一条 `tool` 开一个 open call；一条 `tool_end` **只关闭同 id 且尚未关闭的那一个**。
3. 同 id 的**第二个** `tool_end` = **重复上报**（`duplicateResults`）。
   既不是新配对，也不是新击杀。数据源重连/重放/重复消费都会产生它。
4. 找不到 open call 的 `tool_end` = **孤儿结束**（`orphanResults`）。
   `director` 会补造一个敌人再结算（不丢事件），但**配对统计必须如实记为未配对**。
5. 一直没有 `tool_end` 的 `tool` = **孤儿开始**（`orphanCalls`）。
6. 无 id 的事件按**工具名 FIFO** 配对，单独计入 `anonymousCalls`。

**配对率** = `paired / max(calls, results)`

分母取 `max(calls, results)` 而不是只看 `calls`，是为了防一种很糟的失真：
只报结束、一条开始都没有的数据源，`calls = 0` → 0/0 → 100%，
**最烂的输入显示成最完美的分数**。带上 results 之后是 0/1 = 0%，如实。

数字 id 与字符串 id 视为同一个调用（`7` == `"7"`），因为 `director` 内部
用 `String(ev.id)` 比较。

红线由 `tests/protocol.test.mjs` 锁死，包括一条**直接断言 `paired !== 283`** 的用例。

## 5. 诚实语义红线

协议的设计目标不是"什么输入都收"，而是**"任何失真都必须是可见的"**。

| 情况 | 行为 | 绝不 |
|---|---|---|
| 未知 `kind` | 照收，计入 `unknown`，报出具体名字和次数 | 猜成 `tool`/`tool_end` |
| 缺 `ts`（非实时源） | 拒收，报 `missing-ts` | 用 `Date.now()` 冒充发生时刻 |
| 缺 `ts`（实时源显式给 `now`） | 用接收时刻，标 `tsSource:"ingest"` + warn | 假装那是事件发生时刻 |
| 畸形 JSON | 计数 + 带行号的可读错误，继续读下一行 | 中断整条流 / 静默跳过 |
| 缺必填字段 | 报 `missing-<field>`，说清是哪个 kind 缺哪个 | 填默认值 |
| 快照文件被重写变短 | 报 `revision-changed`，整份重发 | 按"只追加"的假设继续算 |
| 文件/服务打不开 | 明确报错，exit 非 0 | 假装"暂时没有事件" |
| 映射配置一条都没匹配上 | 明确报错 | 输出空事件流当作成功 |

**为什么这么较真**：这个画的每一只敌人、每一次击杀都声称是"真实发生过的"。
一旦协议允许猜字段、补时间、吞坏行，画面上的战果就不再可追溯 ——
那时它和一个手写脚本演的戏没有任何区别，只是更难识破。

## 6. 接入步骤

### 6.1 三步接进来

```
① 选一条通道          ② 让事件过一遍校验        ③ 用 doctor 验收
   file / stdin / http    对得上就用，对不上就改       exit 0 才算接上
```

具体命令见 [`docs/ADAPTERS.md`](./ADAPTERS.md)。

### 6.2 浏览器里手工发事件

```js
__shield.emit({ kind: 'tool', tool: 'read_file', id: 'x1', ts: 0 })
__shield.emit({ kind: 'tool_end', tool: 'read_file', id: 'x1', ok: true, ts: 799 })
__shield.emit({ kind: 'turn_end', ok: true })
```

`main.mjs` 的 `feed()` 是整个程序唯一的输入口。

### 6.3 在浏览器里直接用协议的校验

`protocol/events.mjs` **不依赖任何 `node:` 内建**，可以直接被页面 import：

```js
import { validate, pairReport } from './protocol/events.mjs';
```

这是刻意的：校验规则只能有一份。如果页面里再写一份，两边迟早会分叉。

### 6.4 验收标准

`node tools/doctor.mjs` 对任一数据源必须给出：

- 事件总数 / 分类型计数
- 未知 kind 计数（含名字）
- id 配对率（`paired/max(calls,results)`）
- 重复上报数
- 时间跨度 + 耗时分布（min / median / p90 / max / 不同值个数）
- 坏记录数

**exit 0 = 接上了；exit 1 = 数据有问题；exit 2 = 用法错或源打不开。**

## 7. 版本

`PROTOCOL_VERSION = 1`。

当前没有版本协商机制，因为还没有第二个版本。
真要演进时的原则：**只加可选字段，不改前 6 个字段的语义**。
一旦要改语义（比如让 `ts` 变成微秒），那就是 v2，必须换 `kind` 名或加 `v` 字段，
不能让同一个 `kind` 在不同版本里含义不同 —— 那会让历史数据静默失去可比性。
